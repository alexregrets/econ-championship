# DECISIONS — решения, принятые автономно в этой сессии

Формат: что выбрано → почему. Решения из промптов (Streamlit, lead-role модель,
обёртка вместо замены движка, гибридные ролевые данные) здесь не дублируются —
только то, что пришлось решать самому.

## MVP-дашборд

1. **Создание раунда = `repo.create_round(...)` (DRAFT) + `round_service.open_round(id)`.**
   В `round_service` нет функции «создать раунд», только смена статусов. Промпт
   требовал «форма создания → вызывает round_service.open_round с реальной
   сигнатурой» — реальная сигнатура `open_round(session, round_id)` принимает id
   уже существующего раунда, поэтому создание идёт через репозиторий, открытие —
   через сервис. Ничего не изобретал, использовал оба существующих пути.

2. **Логика страницы вынесена в `dashboard/actions.py`.** Streamlit-страницы
   тяжело тестировать напрямую; асинхронные функции в actions.py тестируются тем
   же стилем, что tests/test_round_service.py. Страница — только формы/таблицы.

3. **`dashboard/db_runner.py`: свежий движок на каждое действие.** Соединения
   aiosqlite привязаны к event loop'у, а `asyncio.run` в синхронном Streamlit
   создаёт новый loop на каждый клик — глобальный движок из `db.session`
   переиспользовать нельзя (упадёт «attached to a different loop»). Для
   однопользовательского инструмента накладные расходы неважны.

4. **«Дедлайн» в списке раундов заменён на `created_at`.** Поля дедлайна в модели
   `Round` нет (см. OPEN_QUESTIONS.md №1); добавлять колонку в БД ради
   отображения — вне скоупа MVP.

5. **`submit_manual_decision` отклоняет решения в не-OPEN раунд.** В репозитории
   такой проверки нет; на уровне UI-действия она обязательна, иначе профессор
   мог бы дописать решение в уже посчитанный раунд и разойтись с Result.

6. **mypy-ошибки в существующих tests/test_repositories.py и
   tests/test_rubric_grader.py (41 шт.) не исправлял.** Они есть уже на
   baseline-коммите (проверено на чистом stash), правка чужих тестов — вне
   скоупа; новый код проходит mypy strict полностью.

## Ролевой трек

7. **Новые таблицы — в отдельном модуле `db/role_models.py`, репозитории — в
   `db/role_repositories.py`.** Существующие `db/models.py` и `db/repositories.py`
   не трогаю (кроме одной строки в `db/session.py`, чтобы новые таблицы
   регистрировались в metadata при создании схемы).

8. **Роли пилота = существующий enum `Role`** (marketer / sales_analyst /
   financier). Промпт предлагал «аналитик / маркетолог / финансист» — это ровно
   он и есть, новый enum не нужен.

9. **Схема ролевых данных.** `CompanyGroundTruth` — один агрегат на
   (round, team): параметры спроса, издержки, референсный общий Q. `RoleDataView`
   — срез на роль: общие для всех ролей поля (`ref_total_quantity`,
   `observed_price` — shared buffer) + приватный сигнал роли
   (`private_signal` + `private_signal_name`) + `cost_share` (сумма долей по
   трём ролям = 1.0 — второй shared-buffer-инвариант). `RoleInput` — ввод каждой
   роли для аудита (Q-предложение + заметка), отдельно от финального `Decision`.
   Типизированные колонки вместо JSON-блоба — как требует промпт.

10. **Формат multi-attribute решения lead-role** (промпт давал «например»):
    `LeadRoleDecision(quantity, price_signal, cost_shares)` — финальный Q задаёт
    lead явно; `price_signal` и `cost_shares` валидируются (сигнал цены не ниже
    нуля, доли ≥ 0 и в сумме 1.0 с допуском), но Q не искажают: слово lead —
    финальное (lead-role модель из промпта). Плюс хелпер
    `aggregate_role_proposals(proposals, weights)` — если lead строит Q как
    взвешенное среднее предложений ролей, веса нормируются. Никакой новой
    экономики: на выходе один float Q, дальше существующий
    `compute_cournot_round` как чёрный ящик.

11. **Ролевой TUI — отдельный модуль `devshell/role_tui.py`**, существующий
    `devshell/tui.py` не трогаю. Тот же Textual-стиль (кнопки + RichLog).
    Groq по умолчанию не вызывается: генератор срезов принимает опциональный
    `StructuredLLM` только для нарративов; без него — детерминированные
    статические тексты (тот же паттерн, что mock-friendly grader).

12. ~~**Ground truth пилота «Нефть РФ 2013»** генерируется из параметров раунда
    (a=100, b=1, mc=10)~~ — **заменено реальными данными, см. №13–15.**
    Приватные сигналы по ролям и фиксированные доли издержек
    (0.55 / 0.25 / 0.20, сумма 1.0) сохранены как были.

## Реальные данные «Нефть РФ 2013» (вторая сессия)

13. **Себестоимость — полная ($50/барр., с НДПИ и капзатратами), не lifting
    cost ($10–15):** движок считает прибыль как (цена − издержки)×объём, и с
    голым lifting cost маржа получалась бы нереалистично огромной.

14. **Единицы движка: объёмы — млн т (как в источнике ЦДУ ТЭК), деньги — $/т
    через стандартный для Urals коэффициент 7.28 барр/т.** Цена
    107.88 × 7.28 = 785.3664 $/т, себестоимость 50 × 7.28 = 364 $/т; прибыль
    тогда автоматически получается в млн долларов. Альтернатива (всё в
    баррелях) дала бы менее узнаваемые студентам объёмы.

15. **Калибровка спроса P = a − b·Q:** наблюдаемая точка 2013 года
    (Q = 203.03 + 86.923 + 61.453 = 351.406 млн т; P = 785.3664 $/т)
    принимается за симметричный Нэш трёх фирм: a = (n+1)·P − n·c = 2049.4656,
    b = (a − P)/Q ≈ 3.5973. Это калибровочное допущение (реальные доли рынка
    асимметричны — см. OPEN_QUESTIONS №6), но оно даёт два проверяемых
    инварианта: точка 2013 лежит на кривой спроса, и Нэш модели воспроизводит
    фактический суммарный выпуск — оба закреплены тестами.

16. **Ролевой пилот сеется отдельным сидером `seed_oil_2013`** (3 реальные
    компании: Роснефть, Лукойл, Сургутнефтегаз — только у них есть данные
    добычи в источнике). Generic-сидер MVP (7 команд со Сбербанком и Яндексом)
    не тронут — симметричный трек работает как раньше. `generate_role_views`
    отказывается работать с командами без реальных данных и с раундом, чьи
    параметры не совпадают с калиброванными: срезы не должны описывать один
    рынок, пока команды играют в другом.
